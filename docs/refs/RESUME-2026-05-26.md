### Wave 12 — M8 #3 batch-rename omap corruption fix (2026-05-26)
**Root cause**: `Transaction::free_block` immediately called `free_one_block_cached`, clearing the bitmap bit in `dirty_bitmaps`. A subsequent `alloc_run_cached` call within the same transaction (for the next rename's new VSB/omap blocks) found that bit as free and re-allocated the block. `free_replaced_metadata` in the later rename called `free_block` again for the same old block (using stale `vsb_raw`/`vol_omap_raw`), but the bit was now 1 again, bypassing the idempotent guard. Double-free corrupted `ChunkFreeRuns`, causing `alloc_run_cached` to re-issue an address already staged in `pending`. At commit, the pending write for that address overwrote the container omap B-tree node or omap header, producing `BadMagic { expected: 11, found: 3 }` on re-open.

**Fix**:
- `free_block` records paddr in `pending_frees: HashSet<u64>` (no bitmap change).
- `commit()` new Step 2a: drain `pending_frees` via `free_one_block_cached` AFTER Step 2 (pending writes flushed). Freed blocks never visible to `alloc_run_cached` within the same transaction.
- Phase B merge: any reclaim bitmaps created by Step 2a are added to `deferred_bitmaps` before Phase B flush (post-NXSB).
- Retained as defence-in-depth: omap_entries dedup by oid (keep last), idempotent-free guard in `free_one_block_cached`.

**S9 regression suite** (`crates/apfs-write/tests/chaos_batch_corruption.rs`):

- `s9_batch_rename_no_omap_corruption_medium` (16 renames) PASS

### Wave 11 — M8 #2 cleanup batching (2026-05-26)

- Direct: `create_file`, `unlink`, `overwrite`, write dirty-buf flush, slow-path truncate.
